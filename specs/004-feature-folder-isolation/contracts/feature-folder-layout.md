# Contract: Feature Folder Layout

**Feature**: [spec.md](../spec.md) | **Date**: 2026-08-22

This is the canonical layout every feature folder MUST follow after this feature is implemented. It is derived from the user's screenshot suggestion (hexagonal core + adapters) and the zelo constitution.

## Canonical template

```text
internal/features/<feature>/
├── core/
│   ├── domain/                 # feature-specific domain types and rules
│   ├── ports/                  # interfaces the core needs (owned by this feature)
│   │   ├── repositories.go     # persistence ports
│   │   └── services.go         # service/helper ports (hashers, tokens, etc.)
│   └── services/               # application use cases (implement the core behavior)
├── handlers/                   # driving adapters: HTTP handlers + RegisterRoutes
├── repositories/               # driven adapters: feature-exclusive persistence (optional)
└── templates/                  # feature-specific Templ views + *_templ.go (optional)
```

## Placement rules

1. **Feature-exclusive code** (used by only this feature) MUST live inside the feature folder (spec FR-002).
2. **Cross-feature code** (used by more than one feature, or by shared middleware) MUST live in `internal/shared/` and MUST NOT be copied into a feature folder (spec FR-003).
3. **Ports are consumer-owned**: each feature declares only the interfaces it needs in its own `core/ports/`. There is no central ports package.
4. **No cross-feature imports**: a feature MUST NOT import another feature's `core`, `handlers`, `repositories`, or `templates` (spec FR-004).
5. **Naming**: `<feature>` is kebab-case and matches the feature name; Go package names match their directory (spec FR-007).
6. **Tests are colocated** with the code they cover (spec FR-008).
7. **Generated files**: `*_templ.go` files are generated by `templ generate` and committed; they are never hand-edited (constitution Principle V).

## Shared modules (v1)

```text
internal/shared/
├── config/          # environment configuration
├── model/           # shared data definitions
├── middleware/      # auth guard, CSRF, logging, recover, security headers
├── security/        # password hashing, session manager, CSRF, token primitives
├── store/           # db open/migrate + multi-feature persistence adapters
├── templates/       # shared layout + error components
├── httpx/           # shared HTTP handler helpers (render, current user/session, CSRF form helper)
└── testutil/        # shared test database helper
```

## Scaffolding new features

Run `scripts/new-feature.sh <feature-name>` to copy the canonical template
(`scripts/_feature-template/`) into `internal/features/<feature-name>/`,
replacing the `{{FEATURE}}` placeholders. After implementing the feature,
wire it in `cmd/web/main.go` and run `scripts/check-feature-boundaries.sh`.

## Boundary checklist (for review)

- [ ] The change touches only one feature folder plus, if needed, `internal/shared/`.
- [ ] No import path crosses from one feature folder into another feature folder.
- [ ] Any code used by a second feature has been moved to `internal/shared/` rather than duplicated.
- [ ] New features were created from this template (spec FR-005).
- [ ] Tests moved with their code and `go test ./...` passes.
