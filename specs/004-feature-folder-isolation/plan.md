# Implementation Plan: Feature Folder Isolation

## Summary

Reorganize the repository's `internal/` tree from its current layer-first layout (`handler/`, `service/`, `store/`, `model/`, `auth/`, `middleware/`, `config/`) into feature-first vertical slices. Each feature gets its own folder under `internal/features/<feature>/` following the hexagonal layout shown in the user's screenshot: `core/` (with `domain/`, `ports/`, `services/`), `handlers/`, `repositories/`, and — to complete the GOTTH vertical slice — `templates/` for feature-specific Templ views. Cross-cutting code that more than one feature uses moves to `internal/shared/`. The public HTTP routes, database schema, migrations, and user-visible behavior MUST remain unchanged; this is a pure internal reorganization.

**Scale/Scope**: ~45 Go files and ~15 Templ files reorganized across 4 feature folders + 1 shared tree; 7 existing migrations untouched

**Structure Decision**: Every feature folder follows the hexagonal shape suggested by the screenshot (`core/{domain,ports,services}` + `handlers/` + `repositories/`), extended with `templates/` so a GOTTH feature is fully self-contained. Shared code moves under `internal/shared/` so the split between "feature-only" and "shared" is visible at a glance. Persistence adapters for tables used by more than one feature (users, roles, invitations, sessions, audit, units) live in `internal/shared/store/` and implement each feature's own port interfaces; only feature-exclusive tables (listings, categories) get adapters inside their feature's `repositories/`. Route registration is per feature (`RegisterRoutes(mux, deps)`), composed in `cmd/web/main.go`, so no feature imports another feature.
